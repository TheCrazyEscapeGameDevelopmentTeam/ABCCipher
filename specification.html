1. 概要

ABC Cipherは、文章やファイルを暗号化・復号するための Webアプリケーションです。

暗号化にはAES-256-GCMを採用しています。 また、文章の暗号文は独自のABCエンコード方式によって、 a・b・cの3種類の文字だけで表現されます。

主な機能

  • 256ビットの暗号鍵の生成
  • 暗号鍵ファイル（.abckey）の保存・読み込み
  • 文章の暗号化・復号
  • ファイルの暗号化・復号
  • 大容量ファイルに対応した分割暗号化
  • 処理の進行状況の表示
  • 暗号化・復号処理のキャンセル

設計上の特徴

文章の暗号文にはABCエンコードを使用し、 ファイルにはバイナリ形式の独自データ構造を使用します。

ファイル暗号化ではデータを1MiB単位に分割し、 各チャンクを個別に認証付き暗号化します。 これにより、ファイル全体を一度に暗号化する方式とは異なり、 分割単位で処理を進めることができます。

2. 基本仕様

項目 仕様
アプリケーション名 ABC Cipher
バージョン v3
暗号化アルゴリズム AES-256-GCM
暗号鍵の長さ 256ビット（32バイト）
認証タグの長さ 128ビット（16バイト）
文章の暗号文形式 ABCエンコード
文章の暗号文に使う文字 a・b・c
鍵ファイルの拡張子 .abckey
暗号化ファイルの拡張子 .abcdata

文章とファイルでは、暗号化前後のデータ構造や IV（初期化ベクトル）の生成方法が異なります。

3. 動作環境

必要な機能

  • JavaScriptが利用できること
  • Web Crypto APIが利用できること
  • File APIが利用できること
  • Blobによるファイル出力に対応していること

セキュアコンテキスト

ABC CipherはWeb Crypto APIを使用します。 このAPIを利用するため、HTTPSまたはlocalhostでの実行を推奨します。

ファイル保存方式

利用環境が対応している場合は、 File System Access APIの showSaveFilePickerを使用して、 保存先を指定しながらファイルを書き込みます。

この機能が利用できない場合は、Blobを作成して ダウンロードする方式に切り替わります。

4. 暗号鍵の仕様

4.1 鍵の生成

暗号鍵はWeb Crypto APIの crypto.getRandomValues()を使用して生成します。

生成される鍵は32バイト、すなわち256ビットです。 これはAES-256-GCMで使用する鍵の長さです。

4.2 鍵の内部表現

鍵はBase64URL形式に変換して扱います。 Base64URLは、通常のBase64で使われる一部の記号を URLで扱いやすい文字に置き換えた形式です。

4.3 鍵ファイル

鍵ファイルの拡張子は .abckey です。 ファイルの内容は次の形式です。 

ABC Cipher Key File
Version: 2
Key: ＜Base64URL形式の暗号鍵＞

鍵ファイルには暗号鍵がそのまま記録されます。 鍵ファイル自体は暗号化されていません。

4.4 鍵の取り扱い

  • 暗号化と復号には同じ鍵を使用します。
  • 鍵を紛失すると、暗号化したデータを復号できなくなります。
  • 鍵ファイルを第三者に渡すと、暗号文を復号される可能性があります。

5. ABCエンコード方式

5.1 概要

ABCエンコードは、バイト列をa・b・cの3種類の文字だけで 表現するための方式です。

この方式では、各バイトを3進数として表現し、 6桁にそろえて文字列に変換します。

5.2 変換規則

3進数の数字 対応する文字
0 a
1 b
2 c

1バイトは0～255の値を持ちます。 3進数6桁では最大729通りの値を表現できるため、 1バイトの値をすべて表現できます。

5.3 データ長

1バイトにつき6文字を使用します。 したがって、変換後の文字列の長さは 元のバイト数の6倍になります。

例えば、元データが10バイトなら、 ABCエンコード後は60文字になります。

5.4 復号時の検証

ABCエンコードされた文字列をバイト列に戻す際には、 次の条件を確認します。

  • 使用されている文字がa・b・cのみであること
  • 文字列の長さが6の倍数であること
  • 各6文字を数値に変換した結果が255以下であること

ABCエンコードは暗号化方式ではありません。 データをa・b・cだけで表現するための符号化方式です。 データの機密性はAES-256-GCMによって確保します。

6. 文章の暗号化方式

6.1 処理の流れ

  1. 入力された文章をUTF-8形式のバイト列に変換する。
  2. 12バイトのランダムなIVを生成する。
  3. AES-256-GCMで暗号化する。
  4. 暗号化結果にヘッダー情報を付加する。
  5. 全体をABCエンコードする。

6.2 暗号化アルゴリズム

項目 値
アルゴリズム AES-GCM
鍵長 256ビット
IV長 12バイト
認証タグ長 128ビット
追加認証データ ASCII文字列 ABCD

6.3 データ構造

現行の文章暗号文は、暗号化されたデータに ヘッダー情報を付加した構造です。

順序 データ 長さ
1 マジック値（ABCD） 4バイト
2 バージョン番号（1） 1バイト
3 IV 12バイト
4 暗号文と認証タグ 可変長

6.4 マジック値とバージョン

マジック値は ABCD です。 データがABC Cipherの現行形式であることを識別するために使用します。

その直後の1バイトはバージョン番号です。 現行の文章暗号文ではバージョン番号1を使用します。

6.5 追加認証データ（AAD）

文章の暗号化では、マジック値 ABCD を AES-GCMの追加認証データ（AAD）として指定します。

AADは暗号化されませんが、認証の対象になります。 そのため、AADが異なる場合は正しく認証されません。

6.6 暗号文の長さ

AES-GCMでは、暗号文の長さは元の平文と同じ長さになり、 さらに16バイトの認証タグが付加されます。

文章暗号文のバイナリデータ全体の長さは、 次のようになります。 

4 + 1 + 12 + 平文のバイト数 + 16

このバイナリデータをABCエンコードするため、 最終的な文字列の長さは上記の6倍になります。

7. 文章の復号方式

7.1 処理の流れ

  1. 入力された暗号文を検証する。
  2. ABCエンコードを解除してバイト列に戻す。
  3. マジック値とバージョン番号を確認する。
  4. IVと暗号文を取り出す。
  5. AES-256-GCMで認証・復号する。
  6. 復号したバイト列をUTF-8形式の文章に変換する。

7.2 認証と復号

AES-GCMでは、復号時に認証タグの検証が行われます。 暗号文や認証に関係するデータが変更されていた場合、 認証に失敗し、復号結果は得られません。

7.3 対応する文章形式

現行形式のほか、旧形式の文章暗号文にも対応しています。 詳細は「11. 互換性」で説明します。

8. ファイル暗号化形式

8.1 概要

ファイル暗号化では、文章暗号化とは異なるバイナリ形式を使用します。 現行形式は ABCD v2 です。

ファイルを1MiB（1,048,576バイト）ずつのチャンクに分割し、 各チャンクを個別にAES-256-GCMで暗号化します。

8.2 データ全体の構造

現行形式のファイルは、次の順番で構成されます。 

┌──────────────────────────────┐
│ ヘッダー（69バイト）          │
├──────────────────────────────┤
│ 暗号化されたメタデータ        │
├──────────────────────────────┤
│ 暗号化されたチャンク 0        │
├──────────────────────────────┤
│ 暗号化されたチャンク 1        │
├──────────────────────────────┤
│             ...              │
├──────────────────────────────┤
│ 暗号化された最終チャンク      │
└──────────────────────────────┘

8.3 ヘッダーの構造

ヘッダーの長さは69バイトです。 各フィールドは次のように配置されています。

オフセット 長さ 内容
0～3 4バイト マジック値「ABCD」
4 1バイト バージョン番号「2」
5～8 4バイト チャンクサイズ
9～16 8バイト 元ファイルのサイズ
17～24 8バイト チャンク数
25～56 32バイト HKDF用ソルト
57～64 8バイト Nonce Prefix
65～68 4バイト 暗号化メタデータの長さ

数値フィールドはビッグエンディアンで記録されます。 つまり、複数バイトの数値は上位バイトから順番に配置されます。

8.4 各フィールドの役割

マジック値

先頭4バイトにはASCII文字列 ABCD が記録されます。 ABC Cipherのファイル形式を識別するために使用します。

バージョン番号

5バイト目には形式のバージョン番号が記録されます。 現行の分割暗号化形式では値2を使用します。

チャンクサイズ

ファイルを分割する際の基本単位です。 現行形式では1MiBを使用します。

元ファイルのサイズ

暗号化前のファイルサイズを8バイトの整数で記録します。 復号時のデータ検証にも使用します。

チャンク数

ファイルを何個のチャンクに分割したかを記録します。 空ファイルの場合は0です。

HKDF用ソルト

ファイルごとの暗号鍵を導出する際に使用する、 32バイトのランダムな値です。

Nonce Prefix

各チャンクのIVを生成するために使用する、 8バイトのランダムな値です。

暗号化メタデータの長さ

ヘッダーの直後に配置される、暗号化済みメタデータの長さを 4バイトで記録します。

9. ファイル暗号化処理

9.1 処理の流れ

  1. 元ファイルの情報を取得する。
  2. ファイル名やMIMEタイプなどのメタデータを準備する。
  3. 32バイトのランダムなHKDF用ソルトを生成する。
  4. 8バイトのNonce Prefixを生成する。
  5. HKDFを使用してファイル専用の暗号鍵を導出する。
  6. ヘッダーを作成する。
  7. メタデータを暗号化する。
  8. ファイルを1MiB単位に分割して暗号化する。
  9. 各データを順番に出力する。

9.2 HKDFによる鍵導出

ファイル暗号化では、読み込んだマスター鍵を直接使用するのではなく、 HKDFによってファイル専用の暗号鍵を導出します。

項目 仕様
鍵導出方式 HKDF
ハッシュ関数 SHA-256
ソルト 32バイトのランダム値
導出鍵の長さ 256ビット

HKDFのInfoには、次の文字列を使用します。 

ABC Cipher chunked file v2 AES-256-GCM

同じマスター鍵を使用しても、ファイルごとに異なるソルトを使うため、 ファイル専用の鍵が導出されます。

9.3 IVの生成

AES-GCMで使用するIVは12バイトです。 先頭8バイトにNonce Prefixを配置し、 残り4バイトにカウンターをビッグエンディアンで配置します。 

IV = Nonce Prefix（8バイト）
   + Counter（4バイト）
用途 カウンター
メタデータ 0
チャンク0 1
チャンク1 2
チャンク2 3
チャンクi i + 1

メタデータと各チャンクで異なるカウンターを使用することで、 同じファイル内でIVが重複しないようにしています。

9.4 メタデータの暗号化

ファイル名とMIMEタイプはメタデータとしてまとめられ、 ファイル本体とは別に暗号化されます。

メタデータには次の上限が設定されています。

項目 上限
ファイル名 4096バイト
MIMEタイプ 1024バイト
メタデータ 8192バイト

メタデータもAES-GCMによる認証付き暗号化の対象です。 そのため、ファイル名などの情報も暗号化ファイル内で保護されます。

9.5 追加認証データ（AAD）

ファイル暗号化では、ヘッダーやデータの種類、 チャンク番号などをAADとして使用します。

メタデータ用AAD

ヘッダー
+ UTF-8("ABCDF2-META")
+ uint32(0)
+ uint64(チャンク数)

チャンク用AAD

ヘッダー
+ UTF-8("ABCDF2-CHUNK")
+ uint32(チャンク番号)
+ uint64(チャンク数)
+ uint32(平文チャンク長)

これらの情報は暗号化されませんが、認証の対象になります。 そのため、ヘッダーやチャンクの順番などが変更された場合、 認証に失敗します。

9.6 チャンクの暗号化

ファイルは最大1MiBずつ読み込まれ、 各チャンクをAES-256-GCMで個別に暗号化します。

AES-GCMでは、各チャンクの暗号文に16バイトの認証タグが付加されます。 そのため、暗号化後のチャンクの長さは次のようになります。 

暗号化後の長さ
= 元のチャンクの長さ + 16バイト

最後のチャンクは、元ファイルの残りのサイズに応じて 1MiB未満になる場合があります。

9.7 チャンク数の計算

チャンク数は元ファイルのサイズから計算します。 

空ファイルの場合：0

それ以外の場合：
ceil(ファイルサイズ ÷ 1,048,576)

ceilは、小数点以下を切り上げる関数です。

9.8 出力ファイルのサイズ

現行形式のファイルサイズは、次の要素から構成されます。 

出力サイズ
= 69
+ 暗号化メタデータの長さ
+ 元ファイルサイズ
+ 16 × チャンク数

69はヘッダーのバイト数、 16 × チャンク数は各チャンクに追加される認証タグの合計です。

10. ファイル復号処理

10.1 処理の流れ

  1. 暗号化ファイルの先頭部分を読み込む。
  2. マジック値とバージョン番号を確認する。
  3. ヘッダーの各フィールドを読み取る。
  4. ファイルサイズやチャンク数などを検証する。
  5. HKDF用ソルトを使用してファイル専用鍵を導出する。
  6. メタデータを読み込み、認証・復号する。
  7. チャンクを順番に読み込み、認証・復号する。
  8. 復号したデータを出力先に書き込む。
  9. すべてのチャンクの処理が完了したら終了する。

10.2 ヘッダーの検証

復号時には、ヘッダーに記録された情報を確認します。 マジック値やバージョン番号が対応していない場合は、 復号処理を続行できません。

10.3 ファイルサイズの検証

ヘッダーに記録された元ファイルサイズとチャンク数、 メタデータの長さなどを使用して、 暗号化ファイル全体のサイズが正しいか確認します。

期待されるファイルサイズは次の式で計算できます。 

69
+ 暗号化メタデータの長さ
+ 元ファイルサイズ
+ 16 × チャンク数

実際のファイルサイズと一致しない場合は、 ファイルが破損している可能性があるため、 正常なファイルとして処理しません。

10.4 チャンクごとの認証

各チャンクは独立してAES-GCMで認証・復号されます。 認証に失敗した場合、そのチャンクの復号結果は使用できません。

メタデータについても同様に認証が行われます。 そのため、メタデータが改変された場合も復号に失敗します。

10.5 空ファイル

元ファイルが空の場合、チャンク数は0になります。 メタデータは通常どおり暗号化されますが、 データチャンクは出力されません。

11. 互換性

11.1 文章暗号文の旧形式

現行の文章暗号文は ABCD v1 形式ですが、 旧形式の ABC2 にも対応しています。

項目 旧形式 現行形式
識別子 ABC2 ABCD
IVの位置 5バイト目から 6バイト目から
IVの長さ 12バイト 12バイト
AAD なし ABCD

旧形式では、先頭4バイトが ABC2 であり、 その後にIVと暗号文が続きます。 旧形式の復号ではAADを指定しません。

11.2 ファイル暗号文の旧形式

ファイル暗号文については、旧形式の ABCD v1 と現行形式の ABCD v2 に対応しています。

項目 ABCD v1 ABCD v2
形式 従来形式 分割暗号化形式
復号方法 ファイル全体を読み込む チャンク単位で読み込む
暗号化単位 ファイル全体 1MiB単位
メモリ使用 ファイル全体を読み込む 分割して処理する

旧形式への対応は復号時の互換性を維持するためのものです。 新しく暗号化するファイルは現行のABCD v2形式で保存されます。

12. セキュリティ上の注意

12.1 暗号鍵の管理

ABC Cipherでは、暗号鍵を利用者自身が管理します。 鍵ファイルには暗号鍵がそのまま保存されるため、 第三者に取得されないように注意してください。

12.2 AES-GCMによる認証

AES-GCMは暗号化と認証を同時に行う方式です。 暗号文が変更された場合などには、認証に失敗します。

12.3 IVの再利用について

AES-GCMでは、同じ鍵でIVを再利用しないことが重要です。 文章暗号化では12バイトのランダムなIVを生成します。

ファイル暗号化では、ファイルごとに導出した鍵とNonce Prefixを使用し、 メタデータと各チャンクに異なるカウンターを割り当てます。

12.4 暗号化とバックアップ

暗号化はデータの機密性を守るための機能であり、 データの消失を防ぐものではありません。 暗号化する前の元データや暗号鍵は、 安全な場所にバックアップすることをおすすめします。

12.5 通信と実行環境

ABC CipherをWeb上で公開する場合は、HTTPSを利用してください。 また、信頼できる環境でアプリケーションを実行してください。

ABC Cipherは暗号化機能を提供するツールです。 すべての攻撃や情報漏えいを防ぐことを保証するものではありません。

13. 制限事項

13.1 ファイルサイズとチャンク数

ファイル暗号化では、チャンク数に上限が設定されています。 

MAX_CHUNKS = 0xfffffffe

これは10進数で4,294,967,294です。 チャンク番号やカウンターを管理するための上限です。

13.2 メモリ使用量

ファイル保存機能が利用できない環境では、 暗号化・復号したデータをBlobとしてまとめてから ダウンロードする方式が使用されます。

この方式では、出力データをメモリ上に保持する必要があります。 そのため、非常に大きなファイルではメモリ不足になる可能性があります。

File System Access APIによるストリーム保存が利用できる環境では、 出力データを順番に書き込むことができます。 ただし、処理中のチャンクなどはメモリ上に保持されます。

13.3 旧形式の復号

旧形式のABCD v1ファイルは、ファイル全体を読み込んでから 復号する方式です。 そのため、大きなファイルではメモリ使用量が増加します。

13.4 キャンセル処理

ファイル処理中にはキャンセル操作ができます。 ただし、Web Crypto APIで実行中の暗号化・復号処理を その場で強制停止することはできません。

そのため、現在実行中の暗号処理が終了した後、 次の処理に進む前などにキャンセルが反映されます。

13.5 ブラウザへの依存

利用できるファイル保存方法はブラウザの対応状況によって異なります。 また、Web Crypto APIを利用できない環境では 暗号化・復号機能を使用できません。

14. エラーとトラブル

鍵が違うか、暗号文が破損しています

使用した鍵が正しくない場合や、暗号文が変更・破損している場合に 発生する可能性があります。 鍵と暗号文を確認してください。

未対応のファイルバージョンです

ファイルのバージョン番号が対応していない場合に発生します。 対応しているABC Cipher形式のファイルか確認してください。

ABCエンコードの形式が正しくありません

文章の暗号文にa・b・c以外の文字が含まれていたり、 文字数が6の倍数でなかったりする可能性があります。

ファイルのサイズが一致しません

ヘッダーに記録された情報と実際のファイルサイズが 一致しない可能性があります。 ファイルが途中で切れていないか確認してください。

Web Crypto APIを利用できません

ブラウザがWeb Crypto APIに対応していないか、 HTTPSまたはlocalhost以外の環境で実行している可能性があります。
